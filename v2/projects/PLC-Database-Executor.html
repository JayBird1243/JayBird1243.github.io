PLC Database Executor

A TwinCAT 3 Structured Text program, added to the existing production line code, that turns live PLC data into validated SQL transactions. A role-aware TwinCAT HMI lets operators see every result and recover from failures.

Role
Wrote the PLC program and HMI controls
Controller
Beckhoff CX51xx · TwinCAT 3
Integration
XML payloads → SQL stored procedures
HMI
TwinCAT HMI, role-based access
  • I wrote the PLC program from scratch in Structured Text: payload builder, transaction handler, response validation and error routing.
  • Every block is a CASE state machine and the HMI shows the current step, so a fault can be traced before anyone opens the code.
  • Operators see database status, error codes and raw responses. Retries and manual stored-procedure calls need an elevated login.
01

Problem

The production database already existed: schema, stored procedures and the expected XML message structure. The line was being commissioned, and its data had to be stored reliably. Operators needed clear error codes on the HMI and failures that were easy to recover from.

02

What I built

PLC program · TwinCAT 3, ST

  1. The main sequence triggers a transaction. PLC variables are mapped into the exact XML structure the stored procedures expect, with string assembly and type formatting done in ST.
  2. The insert is sent and the program waits for the response, with a timeout. The machine is held when it needs database confirmation to continue.
  3. The response is parsed, checked for success and recorded against the transaction.
  4. Failures raise typed error codes to the HMI with the raw database response attached.

Operator HMI · TwinCAT HMI

  • Custom user controls for connection status, last transaction, active error code and response text, built as reusable modules.
  • Operators get read-only status. An elevated login can retry a message or run a stored procedure by hand.
  • Red and yellow are reserved for the E-stop and safety monitor, so nothing on screen competes with a real alarm.
  • Status colours use only 255 or 0 channel values, so they look the same on mismatched shop-floor monitors.
03

Design decisions

  • Each subsystem runs as its own program and coordinates with its neighbours through handshake bits, so each can be developed and maintained on its own.
  • Every function block is a CASE state machine with explicit idle, busy, done and fault states, and the current step is always visible on the HMI.
  • Modular code and comments were part of the deliverable, so the next engineer or technician can maintain it.
04

What I took from it

I worked alongside senior technicians, professional engineers and system integrators. The main lessons were maintainability, modularity and keeping each machine responsible for itself. All of my code was hand-written and checked against Beckhoff InfoSys, with no AI-assisted code generation.
