Daemon Data

A Reddit intelligence platform where users define what to watch and the backend collects it once for everyone who wants it. Scraped posts run through user-built LLM prompts, and the results feed a visual expression graph that decides when to send an alert.

The pipeline

Demand in, alerts out.

Every stage is asynchronous and rate-aware. The interesting engineering sits in the seams: how demand from many users collapses into one scrape, how a scarce pool of Reddit accounts gets shared without collisions, and how LLM work is metered rather than fired off at once.

  1. Workflows capture what each user asks to watch.
  2. Schedulers merge that demand into one plan per subreddit.
  3. The bot pool leases a Reddit account transactionally to run the scrape.
  4. Firestore holds shared posts, delta history, and the analysis queue.
  5. LLM workers drain the queue under a per-user concurrency limit.
  6. The graph evaluator turns the results into a boolean and fires the alert.
01
Shared scrape layer

One scrape plan per subreddit, however many users want it.

A workflow is a request for data, not a job to run. The backend folds every overlapping request into a single scheduler document per subreddit holding the fastest interval, the largest post count, and the widest age window anyone asked for. One scrape satisfies all of them.

The payoff is a clean split between shared facts and private state. Reddit posts exist once, readable by any authenticated user. What a user owns is a thin record of which posts belong to their workflows and what their prompts said about them.

▸ Deep dive

Aggregation

Saving a workflow snapshots the relevant settings into schedulers/{subreddit}, which keeps the per-field maxima across every subscriber plus the union of selected prompt IDs and active notification IDs. If the aggregate changes, the Cloud Scheduler job is recreated with a fresh embedded payload.

Unsubscribing is the harder direction. Stop and expiry both run cleanup tasks that remove the user's entry and recompute the aggregate from whoever is left, so a single heavy user leaving does not silently keep everyone else on their cadence.

Write paths

  • Heavy writes update the canonical post document: title, body, author, permalink, flair, score, comment count, and content fields.
  • Delta writes append time-series points for upvotes and comments under daily subdocuments, with first and second derivatives once there is enough history. This path is batched and deliberately light, because it runs far more often than the heavy one.
  • Queue writes only happen when the workflow enables AI, the flair is eligible, prompts are selected, and the user has credit.

Cadence

Listings are pulled in fixed pages of 100, which is why the user-facing post quantity control snaps to 100-post steps between 100 and 1000. Exposing a control that cannot map onto the underlying call is a good way to make a product feel unpredictable.

02
Bot leasing

Reddit accounts as a transactionally leased resource pool.

A single Reddit account tops out near 100 posts per minute. That ceiling, not compute, is the real constraint on the whole system, so accounts are modelled as leasable resources rather than configuration.

Each account is a Firestore document with an available_at timestamp. A worker samples the pool, picks a candidate, then opens a transaction that re-reads available_at and writes the lease only if the account is still free. Two scrapes starting in the same second cannot land on the same account.

▸ Deep dive

Release is a state machine, not a finally block

  • Success: available_at moves back to now and the account rejoins the pool immediately.
  • Rate limited: available_at is pushed into the future and the lease is not released. The account cools down on its own instead of being handed straight to the next worker.
  • Auth failure or repeated 403: a long lockout, which stops the system from hammering a dead credential or a private subreddit on every cycle.

Advanced scraping splits a user's subreddit list across time and a chosen account budget using Cloud Tasks. When no account is free, the task reschedules around the earliest recovery time with jitter, so fifty tasks waiting on the same account do not all wake up together.

The scaling plan I did not ship

Growing past the pool meant more accounts, and I had a design for getting them. Run the scrape workers across every Firebase Functions region so requests leave from unrelated egress ranges, and provision each account from the region it would later be used from, behind a matching VPN exit, so no two accounts shared an origin.

I scoped it out. Leasing and cooling down a pool is a legitimate response to a rate limit. Deliberately engineering accounts to be hard to associate is account farming, and Reddit's terms are not vague about it. The shipped system stays under the ceiling and queues the overflow, which is slower and defensible.

03
Notification graph

Users draw a boolean expression. The backend compiles and evaluates it.

Metrics, analysis results, constants, arithmetic, and comparisons connect into a graph with one output node. The evaluator walks backward from that output, resolves only the subgraph that actually reaches it, and returns a single boolean.

That backward walk is what makes the feature cheap. A user can leave half-built branches on the canvas and the evaluator never touches them.

▸ Deep dive

Two evaluation modes

Single-post mode publishes as soon as one post satisfies the condition. Time-horizon mode groups values into half-hour buckets, maintains rolling sums across the selected window, and only evaluates the final boolean once enough history has accumulated. A debounce on the tracking key stops the same signal alerting repeatedly.

Firing exactly once

Analysis runs in batches, and a notification cannot be evaluated until the whole batch has left the queued and processing states. The check therefore runs when each worker finishes, which means several workers can reach it at nearly the same moment.

A transaction-backed lock on the batch document resolves it: the first worker to observe a fully drained batch claims the right to publish the evaluation message, and the rest see the claim and drop it. Delivery on top of that is idempotent, so a redelivered Pub/Sub message produces no second alert.

04
Prompt builder

Prompts are typed contracts, not strings.

A prompt is an ordered stack of blocks with a response contract attached: bounded numeric, unbounded numeric, single choice, multiple choice, or free text. The builder compiles the stack into the text sent to the model, and the same contract tells the worker how to parse what comes back.

One definition drives both sides. A user who changes the bounds changes the instruction the model receives and the parser that reads its answer, in one edit, without either drifting from the other.

▸ Deep dive

Blocks

The contract block supplies the header and footer that wrap everything else. Between them sit instruction text, post title and body injectors, a metadata block, and up to five few-shot examples. Compilation resolves the whole stack into one string with {POST_TITLE}-style placeholders that the analysis worker substitutes per post.

Examples validate against the contract

A few-shot example whose expected answer violates the response contract is a silent quality problem, because the model will happily imitate it. The builder checks each example's expected return against the configured bounds or option list and refuses to compile until it matches.

What gets stored

Each result lands on the user's post document keyed by prompt, alongside provider, model, timing, token counts, credits charged, the parsed value, and the bounds it was parsed against. Reanalysis resets prompt completion so a bad result can be overwritten without refetching the post.

05
Metered LLM pipeline

The queue holds the work. Cloud Tasks meters it out.

Scraping never calls a model. It writes queue documents and publishes one kickoff message for the batch. The dispatcher then creates tasks only up to each user's concurrency capacity, and every worker enqueues the next queued item as it finishes.

The queue stays saturated without ever exceeding the limit, and a burst of a thousand posts costs the same steady throughput as a burst of ten.

▸ Deep dive

Provider routing

The worker infers the provider from the model ID and dispatches to OpenAI, Anthropic, or Gemini, with keys held in Secret Manager and never exposed to the client. Users pick a model per workflow or per manual run.

Billing that survives retries

Token usage converts to credits through a pricing table and is deducted transactionally, logged by day and by minute. Billing is tracked per prompt rather than per post, so a task that retries after completing three of five prompts is not charged twice for the three.

The credit gate is checked twice: before tasks are created, and again inside the worker before further model calls. Checking only at dispatch would let a long batch spend well past zero.

Also in the build

The rest of the surface area.

Two providers, one account

Google via Firebase Auth, Discord via a custom OAuth exchange that mints a Firebase token. A Discord login on an existing email links to that account rather than creating a duplicate, and Discord IDs are enforced one-to-one.

Rules as the client boundary

Firestore rules govern what the browser can touch. Credits, subscription state, and protected profile fields are readable but server-written only, so product limits cannot be edited from a console.

Stripe reconciliation

Subscription state is mirrored onto the user document, with plan limits enforced transactionally at creation time so per-user counters stay accurate under concurrent writes.

Heartbeats over hot writes

Scrape runs report progress through a periodic heartbeat document rather than writing on every post, which keeps the dashboard live without creating a contended document.
