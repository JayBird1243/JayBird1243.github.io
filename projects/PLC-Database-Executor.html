PLC Database Executor

A TwinCAT 3 Structured Text application written from a blank project: it turns live PLC data into validated SQL transactions, and a role-aware Beckhoff HMI lets operators see and recover from every result.

  • ControllerBeckhoff CX51xx · TwinCAT 3
  • LanguageStructured Text (IEC 61131-3)
  • IntegrationXML payloads → SQL stored procedures
  • HMITwinCAT HMI · role-based access
← All automation work
  • 01Wrote the entire PLC program from scratch — payload builder, transaction handler, response validation and error routing, all hand-written Structured Text.
  • 02CASE-based state machines throughout, so a fault is located by reading the current step on the HMI rather than stepping through logic online.
  • 03Operators read, engineers write. Custom HMI controls expose DB status, error codes and raw responses; retries and manual stored-procedure calls sit behind an elevated login.

Problem context

The production database already existed — schema, stored procedures, and the XML structure they expected. Nothing on the controller side could talk to it. Process data lived in PLC variables and needed to be inserted reliably, with a clear path for operators to handle failures without waiting for an engineer.

PLC program TwinCAT 3 · ST

  1. Build the payload. Map PLC variables into the exact XML structure the stored procedures expect, including string assembly and type formatting in ST.
  2. Send and wait. Issue the insert, hold on the response with a timeout, and never block the rest of the machine while waiting.
  3. Validate. Parse the response, confirm success, and record the result against the transaction.
  4. Route errors. Failures raise typed error codes to the HMI with the raw database response attached, so the screen says what to do, not just that something broke.

Operator HMI TwinCAT HMI

  • Custom user controls for connection status, last transaction, active error code and response text — built as reusable components, not one-off screens.
  • Elevation-aware: operators get read-only visibility; an elevated login unlocks retry-message and run-stored-procedure actions.
  • Safety-aware colour. Red and yellow were left to the E-stop and safety monitor so nothing on screen competes with a real alarm.
  • Monitor-proof palette. Status colours use only fully saturated channel values (255 / 0) so they render the same on mismatched shop-floor monitors.

Architecture decisions how it's built

  • Smart-machine boundaries. Each subsystem runs as its own program and coordinates with its neighbours through handshake bits, rather than one monolithic codebase. A change in one machine cannot silently break another.
  • State machines as the debugging tool. Every function block is a CASE step machine with explicit idle, busy, done and fault states. The current step is always visible, which turned most support calls into a one-line answer.
  • Modularity and comments as deliverables. Written to be maintained by the next engineer or technician, not just to run.

What I took from it practice

This was a year of working alongside senior technicians, professional engineers and system integrators, and the habits stuck: design the interface bits before the logic, comment for the reader on night shift, and keep each machine responsible for itself. Everything was hand-written and referenced against Beckhoff InfoSys — no code generation, no AI assistance.
